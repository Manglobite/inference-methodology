# Чеклист: приёмка исследования и публикация

> Шаблон. Отмечайте пункты по мере выполнения. Приёмку (содержательную
> проверку) делает независимый ревьюер, а не автор исследования.
>
> Скелет — это **каркас**: обязательные артефакты (профили, промпты, скрипты,
> результаты) появляются на этапе адаптации кейса — скрипты копируются из
> `methodology/scripts/<категория>/`, остальное заполняется автором. Пустые
> каталоги не закрывают пункты ниже.
>
> **Источник и назначение скриптов.** ИСТОЧНИК — `methodology/scripts/<категория>/`
> (`runner/`, `telemetry/`, `report/`, `publish/`). НАЗНАЧЕНИЕ — **плоский**
> `<case>/scripts/` **без подкаталогов категорий**: все скопированные скрипты
> лежат непосредственно в `<case>/scripts/`. Имена `runner`/`telemetry`/`report`/
> `publish` — это категории **источника**, а не каталоги кейса.

## A. Адаптация каркаса (скопировать и заполнить артефакты)

- [ ] **Промпты** заполнены: `prompts/*.json` содержат все использованные
      промпты и конфигурацию генератора лесенки; если пользовательских
      промптов нет — приложен файл с описанием сборки входов.
- [ ] **Профили** заполнены: реальные `profiles/*.json` (не `example.json`);
      генерация зафиксирована (`seed`, `temperature: 0`, `ignore_eos`,
      `n_predict`).
- [ ] **Скрипты** скопированы: нужные скрипты перенесены из категорий
      `methodology/scripts/<категория>/` в **плоский** `<case>/scripts/` (без
      подкаталогов категорий). Всегда: барьер
      `publish/check-public.sh`→`scripts/check-public.sh` и санитайз
      `publish/sanitize-results.sh`→`scripts/sanitize-results.sh`. По
      потребности: `runner/` (раннер и обёртки), `telemetry/`, `report/`.
      Инструкции — `scripts/README.md`.
- [ ] **study.json** заполнен (заголовок, профили с ролями, `ab_planned`,
      `ab_orders`, `ladder_pcts` — из `study.example.json`) либо осознанно
      отсутствует (тогда агрегатор/плоттер автоопределяют профили и метки из
      сырых прогонов).
- [ ] **Результаты** заполнены: сырые прогоны в `results/<run_id>/`.

## B. Приёмка исследования

- [ ] **Цель и гипотезы** сформулированы и проверяемы.
- [ ] **Модель**: источник/URL, commit, sha256, размер, архитектура, лицензия.
- [ ] **Железо**: `HARDWARE.md` заполнен (CPU, RAM, диск, ОС, драйвер,
      тулчейн, таблица GPU).
- [ ] **Рантайм**: движок, commit, флаги сборки, манифест, sha256 бинарей.
- [ ] **Методика**: в скелете ссылка на методику — `../../METHODOLOGY.md`
      (корректна для расположения `templates/research-case/`); после
      копирования кейса в `inference_cases/<case>/` путь меняется на
      `../methodology/METHODOLOGY.md` (или стабильный URL/commit) — сверьте,
      что ссылка не битая; описано, что фиксируется для сопоставимости.
- [ ] **Запуск**: `RUNBOOK.md` воспроизводит полный порядок команд.
- [ ] **Хронология**: `CHRONOLOGY.md` содержит фазы и решения.
- [ ] **Негативные результаты** сохранены и описаны.
- [ ] **Профили** в `profiles/` валидны; пути относительные или `<repo>`.
- [ ] **Промпты** в `prompts/` заполнены (обязательно): все использованные
      промпты и конфигурация генератора лесенки; при отсутствии
      пользовательских промптов — файл с описанием сборки входов.
- [ ] **Скрипты** в **плоском** `<case>/scripts/` (без подкаталогов категорий)
      запускаются из каталога кейса; скопированы нужные скрипты из категорий
      источника (`runner/`, при необходимости `telemetry/`, `report/`; барьер и
      санитайз — из категории `publish/`); ссылки на категории методологии
      (`methodology/scripts/<категория>/`) в `scripts/README.md` актуальны.
- [ ] **study.json** (если используется) согласован с фактическими прогонами:
      имена профилей совпадают с `profile` в `result.json`, роли/порядки/ступени
      заданы; при отсутствии конфига автоопределение корректно.
- [ ] **Сырые прогоны** в `results/<run_id>/` полны (`result.json`,
      `profile.json`, `command.json`, `server.log`, `telemetry.csv`).
- [ ] **Fail-closed `/props`**: раннер сверяет `/props` с профилем (`n_ctx`,
      `total_slots`); при расхождении прогон помечен `non_comparable`, тяжёлые
      запросы пропущены, причина — в `status_reasons`/`props_check`.
- [ ] **Offload-check**: раннер пишет `offload_check`; host model/KV буфер (не
      `CPU_Mapped`, не `CUDA_Host`) или `offloaded X/Y` при X < Y делает прогон
      `non_comparable`; `CPU_Mapped` — mmap весов, не признак offload.
- [ ] **Телеметрия** собирается и сохраняется с прогоном.
- [ ] **Метки времени ступеней**: у ступеней в `result.json` есть
      `started_at_utc`/`finished_at_utc` (UTC, мс, формат как у `timestamp_utc`
      телеметрии) — без них энергия не считается.
- [ ] **Агрегаты**: `docs/results-tables.md`, `docs/results.json`,
      `docs/figures/*.svg` сгенерированы из канонических прогонов; график
      присутствует **при наличии соответствующей измеренной серии**, иначе
      отсутствие объяснено в `README.md`. Пять авто-фигур строит
      `plot_context_curves.py` (`prefill-vs-context`, `decode-vs-context`,
      `ab-cache-hit`, а также `power-vs-load` и `energy-per-token` — при наличии
      энергетической серии); дополнительные графики по осям
      (раскладка/ubatch/спекуляция) строятся автором отдельно.
- [ ] **Фигуры энергии** (при наличии энергетической серии): присутствуют
      `power-vs-load` и `energy-per-token`; иначе их отсутствие объяснено в
      `README.md` (не блокер).
- [ ] **Энергетика** (условно, при наличии телеметрии мощности): per-step
      `energy_j`/`power_avg_w`/`energy_per_output_token_j` (J/request и
      J/output-token из `telemetry.csv`, помечено как **оценка**), агрегированы
      медианой + min/max; baseline `energy_dynamic_j` — из idle-окна (медиана
      суммарной мощности за `IDLE_WINDOW_S` перед первым запросом, fallback —
      минимум по прогону; проверить `idle_baseline_source`/`idle_baseline_w`);
      если телеметрии мощности нет — в отчёте явное «нет данных», это не блокер.
- [ ] **Парный A/B-Δ** (при наличии A/B-серии): присутствует Δ = 100·(B−A)/A по
      совпадающим ступеням с медианой Δ, `n_pairs` и `sign_consistency`; отражён
      в отчёте и в `docs/results.json` (`ab_delta`, ключ `"profile|order"`).
- [ ] **Канонический результат** — агрегат по повторам **на ступень**
      (каноничность per-ступень): ступень входит в агрегат только если она
      comparable (`completion_is_fixed = true` AND `finish_reason = length` AND
      `step_comparable != false`), и по ней **n ≥ 3** уникальных `ok`-прогонов
      (**медиана + min/max**, указаны `n` и список `run_id`).
- [ ] **Ступень-фильтр** применён: ступени с `finish_reason != length` или
      `completion_is_fixed != true` (`step_comparable = false`) в агрегат не
      входят и перечислены с причиной (`step_comparable_reason`) — не отброшены
      молча.
- [ ] **Cold-инвариант** (профиль `cache_prompt = false`): раннер автоматически
      проверил `cache_hit_fraction` против порога `cold_cache_hit_tolerance`
      (порог из профиля, дефолт `0.005`); при превышении порога или неизвестном
      cache-hit ступень помечена не comparable, причина — в
      `step_comparable_reason` (`cold_cache_hit_exceeded`/
      `cold_cache_hit_unknown`), порог сохранён в `result.json`.
- [ ] **Limited вне основной выдачи**: ступени с `n < 3` помечены `limited` и
      выведены отдельным разделом; их нет в основных таблицах и графиках.
- [ ] **Статус прогона по генерации** — `fixed` (все ступени comparable),
      `mixed` (часть) или `variable` (ни одной); у `mixed`-прогонов
      comparable-ступени входят в агрегат, исключённые перечислены отдельно.
- [ ] **Дедупликация вклада**: `n` ступени = число уникальных прогонов; вклад
      одного прогона в одну `target_pct` не дублируется; профильный `n` = число
      прогонов с ≥ 1 comparable-ступенью.
- [ ] **Санитайз путей в `results.json`**: в `docs/results.json` нет абсолютных
      путей — агрегатор скрабит их до `<path>/<basename>`.
- [ ] **Поля ступени**: в `result.json` есть `step_comparable`,
      `step_comparable_reason`, `timing_delta_pct` (prefill/decode) и
      `overhead_s`; расхождение API-vs-лог отражено в отчёте (пороги: ≥ 0.1 %
      значимо).
- [ ] Производные величины помечены как **вычислено**; интерпретация отделена
      от фактов.
- [ ] **Ограничения** и «что не исследовано» описаны.
- [ ] Числа в `README.md` согласованы с `docs/results-tables.md` и `results/`.

## C. Публикация

- [ ] Веса моделей **не** в дереве; опубликованы только URL + sha256.
- [ ] Бинарники/сборки **не** в дереве; опубликованы манифест и скрипт сборки.
- [ ] `bash scripts/sanitize-results.sh` (без флага) не находит маркеров.
- [ ] `bash scripts/sanitize-results.sh --in-place` применён к **публикационной
      копии** дерева (или перед ним сделан архив/бэкап исходных `results/`),
      чтобы не потерять приватные исходные прогоны.
- [ ] `bash scripts/check-public.sh` возвращает `OK: no private markers found`.
- [ ] Нет секретов/токенов/ключей ни в текстах, ни в логах.
- [ ] Нет абсолютных домашних путей (`/home/<user>/`, `/root/`, `/Users/<user>/`)
      и точек монтирования `/mnt/`; только относительные пути и `<repo>`.
- [ ] Нет приватных IPv4-адресов (RFC1918: `10/8`, `172.16/12`, `192.168/16`) и
      маркеров `sk-[A-Za-z0-9_-]{13,}`/`Authorization: Bearer`/`api_key`/`secret`/`token`.
- [ ] Нет имён хостов; узловые имена при необходимости закрыты через
      `PUBLIC_DENY_FILE` (baseline их не покрывает).
- [ ] Guard барьера от таймстампов llama.cpp (`H.MM.mmm.uuu`) сохранён: IP
      подтверждается только по строке с уже снятым ведущим таймстампом.
- [ ] `LICENSE-NOTICE.md` сверен: движок, патчи, модель, скрипты.
- [ ] (Условно: только для монорепозитория; для отдельного репозитория пункт
      неприменим.) Индекс кейсов (`inference_cases/README.ru.md`) обновлён
      ссылкой.
- [ ] `.gitignore` не пропускает нужные артефакты и исключает лишние.
