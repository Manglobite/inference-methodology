# Шаблон публикуемого исследования инференса

**Русский** | [English](TEMPLATE.en.md)

Рабочий скелет-заготовка лежит рядом: `templates/research-case/`.

## 1. Назначение

Этот документ задаёт **минимально достаточный** состав публикуемого
исследования инференса LLM: набор сведений, при котором сторонний читатель
сможет **воспроизвести** прогоны и понять выводы **без автора**. Шаблон
описывает:

- что обязательно должно лежать в каталоге-исследовании;
- в каком формате хранятся профили, сырые прогоны и агрегаты;
- что публикуется, а что нет (веса, секреты, приватные пути);
- как проходит барьер публикации и как адаптировать шаблон под свою модель.

Принцип «минимально достаточно»: лучше меньше артефактов, но каждый — полный и
проверяемый, чем много неполных. Если сведения нет — это фиксируется явно, а не
пропускается молча.

Общая методика измерений описана в [METHODOLOGY.md](METHODOLOGY.md). Описание
конкретного узла-стенда — внутренний материал
[hardware_info/HARDWARE.md](hardware_info/HARDWARE.md), он **не публикуется**;
стенд самого исследования описывает его локальный `HARDWARE.md`
(шаблон — `templates/research-case/HARDWARE.template.md`).

## 2. Обязательный состав публикации (чеклист)

| # | Раздел | Где лежит | Обязательно |
| ---: | --- | --- | --- |
| 1 | Цель и гипотезы | `README.md` (раздел «Цель») | да |
| 2 | Модель: источник/URL, commit, sha256, размер, архитектура, лицензия | `README.md`, `RUNBOOK.md`, `LICENSE-NOTICE.md` | да |
| 3 | Железо | `HARDWARE.md` | да |
| 4 | Рантайм: движок, commit, флаги сборки, манифест, sha256 бинарей | `RUNBOOK.md`, `LICENSE-NOTICE.md`, манифесты вне каталога | да |
| 5 | Методика | ссылка на `METHODOLOGY.md` + локальные детали в `README.md` | да |
| 6 | Запуск/воспроизведение | `RUNBOOK.md` | да |
| 7 | Хронология и негативные результаты | `CHRONOLOGY.md` | да |
| 8 | Профили | `profiles/*.json` | да |
| 9 | Промпты | `prompts/*.json` | да |
| 10 | Скрипты | `scripts/` (копируются из `methodology/scripts/<категория>/`) | да |
| 11 | Сырые прогоны | `results/<run_id>/` | да |
| 12 | Телеметрия | `results/<run_id>/telemetry.csv` | да |
| 13 | Агрегированные таблицы + машинно-читаемая сводка | `docs/results-tables.md`, `docs/results.json` | да |
| 14 | Графики | `docs/figures/*.svg` | условно: график обязателен **при наличии соответствующей измеренной серии**. Три фигуры строит `plot_context_curves.py`: `prefill-vs-context`, `decode-vs-context` (если измерялась лесенка) и `ab-cache-hit` (при A/B). Дополнительные графики по осям (раскладка/ubatch/спекуляция) автор строит отдельно при наличии серии. Если серия не измерялась — график не строится, причина фиксируется в `README.md` |
| 15 | Лицензии | `LICENSE-NOTICE.md` | да |
| 16 | Барьер публикации | `scripts/check-public.sh`, `scripts/sanitize-results.sh` (оба копируются из `methodology/scripts/publish/`) | да |

Дополнительно (по необходимости): `CHECKLIST.md` — приёмка исследования и
публикации; `data/` — небольшие входные данные (sha256, извлечённые кривые,
сводные CSV).

> **Скелет — это каркас, а не готовый кейс.** `templates/research-case/`
> содержит только шаблоны документов, пример профиля, пример конфига
> (`study.example.json`) и заглушки-каталоги (`profiles/`, `prompts/`,
> `results/`, `docs/`, `scripts/` с одним `README.md`). Обязательные артефакты —
> реальные профили, промпты, скрипты и результаты — добавляются на этапе
> адаптации кейса (раздел 9 и `CHECKLIST.md`, разделы A/B). Скрипты **не
> поставляются скелетом**: их копируют из `methodology/scripts/<категория>/`
> (раздел 3, `methodology/scripts/README.md`). Пустые каталоги не считаются
> выполнением пунктов состава.

## 3. Структура директории-исследования

```text
<case>/
├── README.md / README.en.md      <- отчёт: цель, модель, методика, результаты (RU — основной, EN — перевод)
├── HARDWARE.md                   <- конфигурация стенда и минимум для повторения
├── RUNBOOK.md                    <- провенанс весов/рантайма, порядок команд, диагностика
├── CHRONOLOGY.md                 <- фазы, решения и негативные результаты
├── LICENSE-NOTICE.md             <- лицензии движка, патчей, модели, скриптов
├── CHECKLIST.md                  <- чеклист приёмки и публикации
├── study.json                    <- (optional) конфиг агрегатора/плоттера (профили, роли, A/B, ступени)
├── .gitignore                    <- что не коммитится (веса, рантаймы, локальные черновики)
├── profiles/                     <- JSON-профили конфигураций (вход для раннера)
│   └── <profile>.json
├── prompts/                      <- JSON-промпты кейсов (вход для раннера)
│   └── <prompt>.json
├── scripts/                      <- заполняется копированием из methodology/scripts/<категория>/
│   ├── run_cache_sessions.py     <- runner/ (раннер; обёртки run-*-matrix.sh рядом)
│   ├── run-serve-matrix.sh       <- runner/ (запуск профиля: smoke/up)
│   ├── run-bench-matrix.sh       <- runner/ (ladder/A-B + report/plot/check/sanitize)
│   ├── host_telemetry.py         <- telemetry/ (при необходимости отдельного сбора)
│   ├── generate_report.py        <- report/  (агрегация в docs/)
│   ├── plot_context_curves.py    <- report/  (графики в docs/figures/)
│   ├── check-public.sh           <- publish/ (барьер публикации)
│   └── sanitize-results.sh       <- publish/ (санитайз)
├── data/                         <- небольшие входные данные (sha256, кривые, сводки)
│   └── model-checksums.txt
├── docs/                         <- агрегаты (генерируются)
│   ├── results-tables.md
│   ├── results.json
│   └── figures/
│       └── <metric>.svg
└── results/                      <- сырые прогоны (по одному каталогу на прогон)
    └── <run_id>/
        ├── result.json
        ├── profile.json
        ├── command.json
        ├── server.log
        └── telemetry.csv
```

Пояснения:

- **`README.md` — основной человекочитаемый документ.** Все выводы и числа
  находятся здесь; остальные файлы — источник или детализация.
- **`HARDWARE.md`** — стенд, привязка устройств и минимум, при котором
  воспроизведение осмысленно.
- **`RUNBOOK.md`** — точный порядок команд и провенанс (веса, рантайм, манифесты).
- **`CHRONOLOGY.md`** — что пробовали, почему, что не сработало (негативные
  результаты сохраняются, а не удаляются).
- **`profiles/`** — декларативные входы; содержат плейсхолдер `<repo>` вместо
  абсолютных путей.
- **`prompts/`** — тексты/структуры всех использованных промптов; обязателен
  (см. §4.2 и «Политику промптов» ниже).
- **`scripts/`** — весь исполняемый код; ссылается на относительные пути.
  Скелет скриптов **не поставляет**: `<case>/scripts/` заполняется копированием
  из канонических переносимых версий методологии
  (`methodology/scripts/<категория>/`: `runner/`, `telemetry/`, `report/`,
  `publish/`) на этапе адаптации; категории и точные источники — в
  `methodology/scripts/README.md` и `templates/research-case/scripts/README.md`.
- **`study.json`** — опциональный конфиг агрегатора/плоттера: заголовок, список
  профилей с ролями, плановые A/B и ступени лесенки (см. §4.5). При отсутствии
  профили/метки/порядки автоопределяются из сырых прогонов.
- **`data/`** — только небольшие текстовые/CSV-артефакты; веса сюда не кладут.
- **`docs/`** — сгенерированные агрегаты и графики; сырые прогоны не
  перезаписываются агрегатором.
- **`results/`** — сырые прогоны; неудачные сохраняются как есть.

## 4. Форматы файлов

### 4.1. Профиль `profiles/<name>.json`

Профиль описывает одну конфигурацию и является входом раннера. Поля:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `name` | string | Имя профиля (совпадает с именем файла без `.json`) |
| `engine` | string | Движок инференса (`llama.cpp`, `vllm`, …) |
| `model_path` | string | Путь к весам **относительно корня репозитория** |
| `served_model_name` | string | Алиас модели в API |
| `binary` | string | Путь к бинарю сервера |
| `build_variant` | string | Имя варианта сборки (ключ манифеста) |
| `gpu` | object | `{pci_bus_id, cuda_visible_devices, llama_device}` |
| `ctx_size` | int | Размер контекста |
| `parallel` | int | Число параллельных слотов |
| `cache_type_k` | string | Тип KV-кэша для K |
| `cache_type_v` | string | Тип KV-кэша для V |
| `seed` | int | Фиксированный seed генерации (сопоставимость decode) |
| `temperature` | number | Температура генерации (для замеров — `0`) |
| `ignore_eos` | bool | Не останавливаться на EOS; генерировать ровно `n_predict` токенов |
| `n_predict` | int | Число генерируемых токенов (фикс для сопоставимости) |
| `port` | int | Порт сервера |
| `command_env` | object | Переменные окружения запуска |
| `command` | array[string] | Фактическая команда; `<repo>` — плейсхолдер корня |
| `note` | string | Человекочитаемая заметка о назначении профиля |
| `vram_note` | string | Измеренная раскладка VRAM (буферы, пик, запас) |

Генерация фиксируется обязательно: `seed`, `temperature: 0`, `ignore_eos: true`
и `n_predict` (признак корректности — `finish_reason = length`,
`completion_is_fixed = true`). `--seed` и `--n-predict` дублируются в
`command`; `temperature`/`ignore_eos` раннер передаёт в теле запроса к API
(у `llama-server` это per-request параметры). Режимные флаги, важные для
сопоставимости и воспроизведения, также входят в `command` и профиль:
`--fit off`, `--kv-offload`, `--flash-attn on`, `--cache-prompt`,
`--cache-ram`, `--kv-unified`, `--timeout`, `--metrics`, `--reasoning off`.

> **Полный фактический `command` — источник истины.** Поля-сводки (`ctx_size`,
> `cache_type_*`, `seed`, `n_predict`, режимные флаги) должны совпадать с
> командой; при расхождении верна команда, а поля нужно поправить.

Пример — `templates/research-case/profiles/example.json` (валидный JSON с
полем `_note`, содержащим подсказки по заполнению; расширен до полноты
реального профиля-образца).

### 4.2. Промпты `prompts/*.json`

Промпты обязательны, даже если кейс их «не использует». Каталог `prompts/`
фиксирует всё, чем генерировался вход, чтобы читатель мог воспроизвести
запросы:

- тексты/структуры промптов для каждой ступени и режима (JSON);
- конфигурацию генератора лесенки (единицу-заполнитель/`FILLER_UNIT`,
  префикс, способ усечения по токенам — см. `METHODOLOGY.md` §4.3);
- параметры запроса (роль, формат сообщений, `max_tokens`).

Если пользовательских промптов нет, приложите файл с описанием сборки входов
(чем генерировался промпт, какие ступени, какой tokenizer/сервис
`/tokenize`). Пустой `prompts/` не допускается.

### 4.3. Состав прогона `results/<run_id>/`

`<run_id>` — `<timestamp>-<profile>-<mode>`, например
`20260101-120000-<profile>-ladder`.

| Файл | Назначение |
| --- | --- |
| `result.json` | Итог прогона: статус, ошибка, ступени (prefill/decode, cache-hit, фикс генерации), максимумы телеметрии, частоты |
| `profile.json` | Копия использованного профиля (фиксирует вход как есть) |
| `command.json` | Фактическая команда, окружение, порт, seed, режим/порядок |
| `server.log` | stdout+stderr сервера (буферы, предупреждения, ошибки) |
| `telemetry.csv` | Сэмплы (обычно 0.5 с): RAM/swap, CPU, температура, по каждому GPU — температура/загрузка/память/мощность; память процесса |

Неудачные прогоны сохраняются со `status = failed` и текстом ошибки; они не
удаляются и не перезаписываются.

### 4.4. Агрегаты `docs/`

| Файл | Назначение |
| --- | --- |
| `docs/results-tables.md` | Человекочитаемые сводные таблицы по каноническим прогонам |
| `docs/results.json` | Машинно-читаемая сводка: список прогонов, канонические/контрольные, ступени |
| `docs/figures/*.svg` | Графики (prefill/decode/сравнения); по языку — `*.ru.svg` / `*.en.svg` |

Агрегаторы **read-only** по отношению к `results/`: они только читают сырые
прогоны и пишут в `docs/`. Каноническим для конфигурации/ступени считается
**агрегат по повторам**: **n ≥ 3** успешных (`ok`) прогонов, агрегация —
**медиана + min/max**, в `docs/results.json` фиксируются `n` и список `run_id`
всех вошедших прогонов. При `n < 3` результат помечается
ограниченным/неканоническим. Правило выбора и список канонических/контрольных
прогонов фиксируются в `docs/results.json`; норма — в `METHODOLOGY.md` §11.1
(выбор канонического прогона и агрегация), графики — §11.2.

> **Ограничение референс-реализации.** Раннер-образец выбирает «последний
> успешный» прогон и не агрегирует повторы. Это ограничение референса, а не
> норма: нормативный минимум — агрегация по повторам (n ≥ 3, медиана + min/max).

### 4.5. Конфиг исследования `study.json`

`study.json` (пример — `templates/research-case/study.example.json`) —
опциональный вход агрегатора `generate_report.py` и плоттера
`plot_context_curves.py`; задаёт представление отчёта и графиков. Поля:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `title` | object | Заголовок исследования `{ru, en}` (шапка отчёта, подписи графиков) |
| `profiles` | array | Список вариантов: `{name, label{ru,en}, role}`; `name` совпадает с `profile` в `results/<run_id>/result.json`, `role` — `main` (основная серия) или `control` (контрольная) |
| `ab_planned` | array[string] | Профили, для которых обязательна A/B-серия по cache-hit |
| `ab_orders` | array[string] | Ожидаемые строки порядка A/B (например, `ABAB`, `ABBABAA`) |
| `ladder_pcts` | array[int] | Ступени заполнения контекста (процент от `ctx`), которые должна покрывать лесенка |

Отсутствие файла **допустимо**: агрегатор и плоттер автоопределяют профили,
метки, порядки A/B и ступени из сырых прогонов (все профили становятся `main`).
Списки `ab_planned`/`ab_orders`/`ladder_pcts` также опциональны. Конфиг
отыскивается как `./study.json`; путь переопределяется `--config`.

## 5. Что публикуется, а что нет

| Артефакт | Публикация |
| --- | --- |
| Веса моделей | **не коммитить**; публикуются только URL, commit, размер и sha256 |
| Рантаймы/бинарники/сборки | не коммитить; публикуются манифест (commit, флаги, sha256) и скрипт сборки |
| Сырые логи и `results/` | только **после санитайза** публикационной копии (`scripts/sanitize-results.sh --in-place`; скрипт копируется из `methodology/scripts/publish/`). `--in-place` перезаписывает файлы, поэтому применяйте его к **копии для публикации** или предварительно сделайте архив/бэкап исходных `results/` — приватные исходные прогоны не должны быть потеряны |
| Секреты, токены, ключи | **никогда** (ни в текстах, ни в логах) |
| Абсолютные домашние пути | **никогда**; только относительные пути и `<repo>` |
| Имена хостов, внутренние IP | **никогда** |
| Проприетарные драйверы/модули | **никогда**; только ссылка и tag источника |
| Скрипты, профили, документация | публикуются «как есть» (обычно MIT), с уведомлением в `LICENSE-NOTICE.md` |

Лицензии сторонних компонентов (движок, патчи, модель) сводятся в
`LICENSE-NOTICE.md`; для каждого — лицензия, источник и что именно
переиспользуется.

## 6. Барьер публикации

Перед выкладкой каталог проходит два инструмента. Оба копируются в
`<case>/scripts/` из `methodology/scripts/publish/` (см.
`methodology/scripts/README.md`):

1. **`scripts/check-public.sh`** — рекурсивный обход дерева кейса с исключением
   служебных каталогов (`.git/`, `build/`, `dist/`, `__pycache__/`,
   `node_modules/`, `*.pyc`). По каждому файлу — `grep` по обобщённым паттернам:
   домашние пути (`/home/<user>/`, `/root/`, `/Users/<user>/`), точки
   монтирования (`/mnt/`), приватные IPv4 (RFC1918: `10/8`, `172.16/12`,
   `192.168/16`), секреты по точному паттерну `sk-[A-Za-z0-9_-]{13,}`,
   заголовок `Authorization: Bearer` и присваивания
   `api_key`/`secret`/`token`.
   Возвращает **exit 2** при находке или ошибке сканирования, **exit 0** только
   при чистоте (fail-closed). Паттерны расширяются через `PUBLIC_DENY_FILE`,
   ложные срабатывания снимаются `.public-allow`; запуск —
   `bash scripts/check-public.sh`. **Имена хостов и внутренние идентификаторы
   baseline не покрывает:** их добавляют через `PUBLIC_DENY_FILE` и/или
   проверяют вручную при ревью публикации.
2. **`scripts/sanitize-results.sh [--in-place]`** — без флага только сообщает о
   находках и падает (exit 2); с `--in-place` перезаписывает приватные пути,
   имена, хосты и секреты в `results/`, `docs/`, `prompts/` и top-level
   `*.md/*.json/*.csv/*.log`. Применяйте `--in-place` к **публикационной копии
   дерева** (или сделайте архив/бэкап исходных `results/` перед запуском):
   команда деструктивна и может стереть приватные исходные прогоны.

Политика и исключения:

- Санитайз и барьер должны давать **одинаковый вердикт** на одном дереве —
  паттерны детекции держатся синхронно.
- **Loopback `127.0.0.0/8` не является приватным маркером** (сервер слушает
  локально).
- **Таймстампы прогресса llama.cpp вида `H.MM.mmm.uuu`** визуально похожи на
  IPv4-адрес, но таковым не являются; первое поле таймстампа может попадать в
  `10`, то есть в диапазон `10/8`. Поэтому общий IPv4-паттерн не применяется
  вовсе, а RFC1918-скан барьера защищён **guard'ом**: ведущий токен таймстампа
  снимается со строки, и IP-находка подтверждается только если после этого в
  строке остаётся реальный адрес (остальные паттерны проверяются по исходной
  строке и не ослабляются). При санитайзе ведущий таймстамп прячется за
   временный маркер. Пример такого guard'а реализован в
   `methodology/scripts/publish/check-public.sh`.
- Внутренние проектные маркеры (имена пакетов/каталогов control plane) в
  публикацию не попадают и заменяются плейсхолдерами.

## 8. Чеклист публикации

1. `HARDWARE.md` заполнен: CPU, RAM, диск, ОС, драйвер, тулчейн, таблица GPU
   (модель, PCI bus, VRAM, compute, роль).
2. Провенанс модели зафиксирован: URL, commit, размер и sha256 каждого файла;
   веса отсутствуют в дереве.
3. Провенанс рантайма зафиксирован: движок, commit, флаги сборки, манифест,
   sha256 бинарей; бинарники отсутствуют в дереве.
4. `RUNBOOK.md` воспроизводит полный порядок команд и содержит диагностику.
5. `CHRONOLOGY.md` содержит фазы, решения и негативные результаты.
6. Профили в `profiles/` валидны, реальны (не `example.json`) и используют
   `<repo>`/относительные пути; генерация зафиксирована (`seed`,
   `temperature: 0`, `ignore_eos`, `n_predict`).
7. `prompts/*.json` заполнены: все использованные промпты и конфигурация
   генератора лесенки; если пользовательских промптов нет — приложен файл с
   описанием сборки входов.
8. Скрипты скопированы из `methodology/scripts/<категория>/` в
   `<case>/scripts/` и запускаются из каталога кейса: раннер + обёртки
   (`runner/`), телеметрия на месте, агрегатор и графики (`report/`), барьер
   (`check-public.sh`) и санитайз (`sanitize-results.sh`) — из `publish/`;
   см. `methodology/scripts/README.md`.
9. `study.json` (если используется) описывает заголовок, профили с ролями,
   `ab_planned`/`ab_orders` и `ladder_pcts`; при его отсутствии автоопределение
   из сырых прогонов даёт корректные профили и метки.
10. `docs/results-tables.md`, `docs/results.json` и графики сгенерированы из
    канонических прогонов. Канонический результат — агрегат по **n ≥ 3**
    успешным прогонам (**медиана + min/max**, зафиксированы `n` и список
    `run_id`); при `n < 3` результат помечен ограниченным/неканоническим.
     График обязателен **при наличии соответствующей измеренной серии**: три
     автоматически генерируемые фигуры `plot_context_curves.py`
     (`prefill-vs-context`, `decode-vs-context` — если измерялась лесенка;
     `ab-cache-hit` — при A/B), а дополнительные графики по осям
     (раскладка/ubatch/спекуляция) автор строит отдельно при наличии серии.
     Если серия не измерялась — график не строится, причина фиксируется
     в `README.md`.
11. `bash scripts/sanitize-results.sh` (без флага) не находит маркеров.
12. `bash scripts/sanitize-results.sh --in-place` применён к **публикационной
    копии** дерева (или перед ним сделан архив/бэкап исходных `results/`), чтобы
    не потерять приватные исходные прогоны.
13. `bash scripts/check-public.sh` возвращает `OK: no private markers found`.
14. `LICENSE-NOTICE.md` сверен: движок, патчи, модель, скрипты.
15. В публикуемых текстах — только относительные пути и плейсхолдеры; имена
    хостов, внутренние IP и секреты отсутствуют.
16. (Условно: только для монорепозитория; для отдельного репозитория пункт
    неприменим.) Индекс кейсов (`inference_cases/README.ru.md`) обновлён
    ссылкой на новый кейс.

## 9. Как адаптировать шаблон под свою модель/железо

Скелет — это **каркас**: скопируйте `templates/research-case/` в новый каталог
кейса, затем **добавьте обязательные артефакты** и заполните плейсхолдеры.

Заполните:

| Что | Заменить на |
| --- | --- |
| `<MODEL>` | имя модели во всех документах |
| `<HARDWARE>` | краткое имя стенда (например, `2xCMP50HX+RTX2080Ti`) |
| `<CTX>` | размер контекста (например, `262144`) |
| `<RUNTIME>` | имя варианта рантайма (ключ манифеста) |
| `<repo>` | корень вашего inference-репозитория при запуске |
| `profiles/example.json` | реальные профили конфигураций |
| `study.example.json` | `study.json` с вашими профилями/ролями (или удалите файл — автоопределение) |
| `prompts/.gitkeep` | реальные `prompts/*.json` (все использованные промпты) |

Скопируйте скрипты из методологии в `<case>/scripts/` (в скелете их нет):

- раннер и обёртки — `methodology/scripts/runner/` (`run_cache_sessions.py`,
  `run-serve-matrix.sh`, `run-bench-matrix.sh`);
- телеметрия — `methodology/scripts/telemetry/host_telemetry.py` (при
  необходимости отдельного сбора; раннер собирает телеметрию сам);
- агрегатор и графики — `methodology/scripts/report/` (`generate_report.py`,
  `plot_context_curves.py`; график строится только **при наличии
  соответствующей измеренной серии** — см. §2, §8);
- барьер и санитайз — `methodology/scripts/publish/` (`check-public.sh`,
  `sanitize-results.sh`) — нужны всегда.

Затем добавьте реальные профили, промпты и сырые прогоны (`results/`).

Затем сверьте:

- `HARDWARE.md` — реальные PCI bus ID, VRAM, compute capability, драйвер;
- `RUNBOOK.md` — фактические команды скачивания и проверки sha256;
- `profiles/` — пути модели/рантайма и привязку `CUDA_VISIBLE_DEVICES`;
- `scripts/` — пороги телеметрии, порты, режимы прогонов;
- `LICENSE-NOTICE.md` — лицензии именно вашей модели и патчей;
- `check-public.sh` / `sanitize-results.sh` — под ваши приватные маркеры (и
  сохраните guard барьера от таймстампов llama.cpp).

После заполнения пройдите чеклист раздела 8.
