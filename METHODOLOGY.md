# Методология исследования локального инференса LLM

**Русский** | [English](METHODOLOGY.en.md)

> Переносимая, не привязанная к оборудованию методика. Позволяет другому
> исследователю или агенту на **другом железе** и **другой модели** провести
> максимально объективно сопоставимое исследование локального инференса LLM.
> Все конкретные числа, имена и пути стенда ниже — только **примеры** (помечены);
> обязательны принципы, протокол и состав артефактов, а не значения.

- **Аудитория.** Агент-исполнитель (проводит прогоны и пишет артефакты) и
  человек-исследователь (ставит задачу, интерпретирует, публикует).
- **Как пользоваться.** Прочитайте разделы 1–2, пройдите чеклист раздела 0,
  затем ведите эксперимент по разделам 3–12. Разделы 13–16 — перед публикацией
  и разбором результатов.
- **Перекрёстные документы.** `hardware_info/HARDWARE.md` — описание конкретного
  стенда и матрица параметров (заполняется под своё железо); `TEMPLATE.md` —
  упаковка публикуемого кейса.
- **Инструменты.** Переносимые скрипты методологии лежат в `scripts/` по
  категориям: `scripts/runner/` (прогоны), `scripts/telemetry/` (телеметрия),
  `scripts/report/` (агрегация и графики), `scripts/publish/` (барьер и
  санитайз). Они не привязаны к железу и кейсу и копируются в `<кейс>/scripts/`
  (см. `scripts/README.md`).
- **Плейсхолдеры.** `<MODEL>` — модель; `<MODEL_PATH>` — путь к файлу весов;
  `<CTX>` — конфигурируемый контекст; `<GPU>` — ускоритель, `<GPU_LIST>` — список
  ускорителей (например, `nvidia-smi -i <GPU_LIST>`); `<RUNTIME>` — сборка/вариант
  рантайма, `<SERVER_BINARY>` — путь к бинарю сервера; `<PORT>` — порт сервера;
  `<DEVICE_LIST>` — порядок устройств для `--device`; `<SEED>` — фиксированный
  seed; `<N_PREDICT>` — фиксированная длина генерации; `<CONTROL_PLANE_URL>` —
  адрес control-plane вашего узла; `<RESULTS_DIR>` — каталог результатов;
  `<CACHE_RAM>` — размер host prompt-кеша (`--cache-ram`).

**Пометки достоверности** (обязательны для каждого утверждения-эффекта):

| Пометка | Значение |
| --- | --- |
| **измерено** | прямое значение прибора, серверного тайминга или телеметрии |
| **вычислено** | арифметика над измеренным (Δ, проценты, запас) |
| **интерпретация** | причинное объяснение, не следующее напрямую из данных |

## 0. Быстрый старт агента (чеклист)

1. Проверить свободные `<GPU>` и место на диске (`nvidia-smi`, `df -h`).
2. Выполнить стендовые адаптеры — остановить прод-бэкенд и снять парковку
   частот/VRAM, только если это применимо на вашем стенде (раздел 2).
3. Зафиксировать провенанс: commit и флаги сборки `<RUNTIME>`, sha256 и размер
   `<MODEL>`, версии драйвера и CUDA, топологию/порядок `<GPU>`, CPU/RAM/ОС.
4. Собрать профиль конфигурации: явно разделить фиксированные и варьируемые
   параметры (раздел 3).
5. Выполнить smoke-пробу: загрузка, `/props` (`n_ctx = <CTX>`), один короткий
   запрос, пик VRAM.
6. Убедиться, что модель **и** KV целиком в VRAM (раздел 5); иначе не измерять
   скорости, пока не устранено.
7. Запустить `ladder`-лесенку на первой конфигурации (раздел 4).
8. Для сравнимых конфигураций — A/B-режим в одном порядке, затем в обратном
   (`ABAB` и `ABBABAA`), внутри одной сессии.
9. Повторить ключевые прогоны: канонический результат требует **n ≥ 3**
   успешных (`ok`) прогонов на **ступень** (каноничность per-ступень, раздел
   11.1). Сохранить **все** прогоны, включая неудачные, со статусом (`ok |
   failed | timeout | non_comparable`, раздел 7).
10. Свести машинно-читаемую сводку и таблицы, построить обязательные графики,
    пометить измеренное/вычисленное/интерпретацию, пройти барьер публикации
    (разделы 11, 15).

## 1. Инварианты исследования

| Инвариант | Зачем | Как проверить |
| --- | --- | --- |
| Один тяжёлый процесс за раз | исключить взаимное искажение прогонов | `nvidia-smi` перед стартом; раннер отказывается стартовать второй сервер |
| Модель **и** KV целиком в VRAM | не измерять вытеснение вместо скорости | `/props`, строки лога, запас VRAM (раздел 5) |
| Параллельность 1 (`--parallel 1`) | стабильные тайминги, один слот и prompt-кеш | флаг профиля; `/props` → `total_slots` |
| Детерминизм: `temperature 0`, фиксированный `seed`, фиксированная длина генерации | сопоставимость decode между прогонами | `ignore_eos` + `n_predict`; `finish_reason = length` |
| Одна ось за раз | не смешивать эффекты | сравнение различается ровно одним параметром |
| A/B-чередование внутри одной сессии | убрать дрейф частот/температур между «эпохами» | порядок `ABAB`/`ABBABAA`, а не «сначала все A, потом все B» |
| Сырые серверные тайминги — основная метрика | метрика самого движка, не сети | парсить `prompt eval time` / `eval time` из `server.log` |
| HTTP end-to-end — подтверждающая метрика | ловит накладные и таймауты | `elapsed` клиента рядом с серверными таймингами |
| Телеметрия всегда | пик VRAM, запас, температуры, RAM/swap | `telemetry.csv` (раздел 10) |
| Неудачные прогоны не удаляются | сохранить негативный результат и причину | каталог прогона со статусом (`failed`/`timeout`/`non_comparable`) |
| Факт отделён от интерпретации | читаемость и проверяемость | пометки измерено/вычислено/интерпретация |

**Правило.** Если условие инварианта нарушено, результат помечается статусом
`non_comparable` и в основные таблицы/графики не входит (но сохраняется как
есть). Полная политика статусов прогонов — в разделе 7.

## 2. Предполёт (preflight)

Порядок обязателен; каждый пункт фиксируется в артефактах прогона.

### 2.1. Обязательные предполётные проверки

1. **Свободные `<GPU>`.** `nvidia-smi -i <GPU_LIST>` — нет чужих тяжёлых
   процессов; VRAM свободна. Один тяжёлый процесс за раз.
2. **Диск.** `df -h` для корня и отдельно для тома с весами (`<MODEL_PATH>`):
   должно хватать на `<MODEL>` плюс артефакты сборки/прогонов.
3. **Smoke-проба.** Поднять сервер, проверить `/props` (`n_ctx = <CTX>`,
   flash-attention), послать один короткий запрос, снять пик VRAM, остановить
   сервер. Защита от OOM на многочасовых прогонах.
4. **Провенанс** (записать до старта, в машинно-читаемый файл):

| Поле | Что фиксировать |
| --- | --- |
| Рантайм | commit, ветка/форк, флаги сборки, путь и sha256 бинаря, вариант `<RUNTIME>` |
| Модель | источник, commit ревизии, имя файла, размер в байтах, sha256 |
| Драйвер/CUDA | версия драйвера, версия CUDA, архитектуры сборки (`CMAKE_CUDA_ARCHITECTURES`) |
| Топология | список `<GPU>`: модель, VRAM, PCI bus id, compute capability, линки (PCIe gen/width, P2P) |
| Порядок устройств | `CUDA_DEVICE_ORDER=PCI_BUS_ID` и фактический `--device` |
| Хост | CPU (модель/число потоков), RAM, swap, ОС/ядро |

### 2.2. Стендовые адаптеры (только если применимо на вашем стенде)

Эти шаги зависят от инфраструктуры конкретного узла; на другом стенде они могут
отсутствовать.

1. **Остановка прод-бэкенда.** Через control-plane вашего узла
   (`<CONTROL_PLANE_URL>`): найти PID и остановить. Если control-plane нет —
   остановить вручную. Прод не трогать без решения владельца.
2. **Снятие idle-парковки частот.** Если control-plane паркует `<GPU>` в
   простое (пример: до 300 МГц) и удерживает VRAM, отключить парковку на время
   серии и разбудить карты. **Интерпретация:** при запаркованной карте все замеры
   недействительны. После серии вернуть прежнюю политику. Сброс частот
   `nvidia-smi -i <GPU_LIST> -rgc` применять только если это применимо и
   разрешено на вашем стенде.

## 3. Оси эксперимента

| Ось | Что варьируется | Что обязано быть фиксировано при сравнении |
| --- | --- | --- |
| KV-квант | `--cache-type-k` / `--cache-type-v` (`f16`, `q8_0`, `q4_0`, …) | веса, `<CTX>`, раскладка, рантайм |
| Квант весов | файл `<MODEL>` (`Q4_K_M`, `Q8_0`, …) | KV-квант, `<CTX>`, раскладка |
| Раскладка по `<GPU>` | число карт, `--split-mode`, `--tensor-split`, `--device` | веса, KV, `<CTX>` |
| µbatch | `--ubatch-size` | веса, KV, `<CTX>`, остальные env |
| Спекуляция/MTP | включение и глубина (`--spec-draft-n-max`) | базовый decode без спекуляции как контроль |
| Размер контекста | `<CTX>` | веса, KV-квант, раскладка |
| Вариант рантайма/сборки | `<RUNTIME>` (baseline vs патч) | модель, KV, `<CTX>`, раскладка |
| Порядок устройств | `--device` (порядок карт) | всё остальное; проверять байт-идентичность вывода |
| Prompt-кеш | `cache_prompt` (`true`/`false`) | веса, KV, `<CTX>`, раскладка; при `false` — инвариант `cache_hit ≈ 0` |

**Правило одного изменения.** Одно сравнение — ровно одно различие. Если свип
меняет несколько параметров сразу, это **конфаунд**: его вклад не отделён, и
такой вывод помечается как несопоставимый (см. раздел 16).

## 4. Принцип лесенки (ladder) — центральный раздел

**Определение.** `ladder` — последовательность запросов в **одной серверной
сессии**, в которой заполнение контекста растёт ступенями, а метрики снимаются
на каждой ступени.

### 4.1. Ступени

- Ступени: **0 / 10 / 30 / 60 / 80 %** от `<CTX>`.
- Ступень **0 %** — короткий прогрев (пример: «Привет», ~12 токенов). Она
  **исключается из анализа**: показывает разовый эффект старта. Число токенов
  прогрева — ожидаемое/проверяемое, а не универсальная константа; сохранять
  фактические token counts прогрева.
- В анализ входят ступени 10–80 %. Пример (не обязателен): при
  `<CTX>` = 262144 это 26214 / 78643 / 157286 / 209715 токенов.

### 4.2. Кумулятивность ступеней

Ступени идут **одной сессией** и используют **общий префикс**: каждая следующая
ступень — расширение предыдущего промпта. Это добавки (пример: +10 / +20 / +30 /
+20 п.п. к заполнению), а не независимые уровни. **Гипотеза (ожидаемое,
проверяемое):** из-за общего префикса `cache_hit_fraction` растёт по ступеням.
Это не универсальный факт: сохранять фактические token counts каждой ступени и
**фиксировать немонотонность**, если она наблюдается.

### 4.3. Детерминированная сборка промптов

- Промпт строится расширением префикса: базовый префикс + повторяющийся
  филлер, обрезанный так, чтобы число токенов не превышало цель.
- Число токенов сверяется с сервером (`/tokenize`), а не оценивается по байтам.
- Для каждой ступени проверяется, что новый промпт начинается с предыдущего
  (флаг `prompt_prefix_ok`). Это гарантирует переиспользование префикса.
- Сборка должна быть воспроизводимой: один и тот же вход даёт тот же промпт.

### 4.4. Семантика `cache_hit_fraction`

- `cache_hit_fraction` — доля промпта, взятого из кеша:
  `1 − evaluated_tokens / prompt_tokens` (или `cache_n / (cache_n + prompt_n)`).
- **Гипотеза (ожидаемое, проверяемое):** доля растёт по кумулятивным ступеням,
  потому что префикс переиспользуется; на первой ступени ожидается 0. Это не
  гарантированный факт: сохранять фактические token counts и фиксировать
  немонотонность.
- Сравнивать конфигурации по скорости можно **только при равной длине промпта**
  (равном заполнении). Значения prefill/decode на разных ступенях между собой
  не сравнивать.
- **Опциональный cold-режим.** Профиль может задавать `cache_prompt = false`
  (настраиваемая ось, раздел 3). Тогда действует жёсткий инвариант
  `cache_hit ≈ 0` на всех ступенях; при его невыполнении ступень помечается
  `non_comparable`. Cold-режим не расширять до полного протокола — только как
  отдельная ось сравнения.

### 4.5. Адаптация под свой `<CTX>`

- Доли ступеней (10/30/60/80 %) переносимы; абсолютные длины — нет.
- Сетка ступеней может задаваться профилем (`ladder_pcts`, читается раннером из
  профиля; см. также `study.json`, раздел 11.2); если она задана, она
  **первична** по отношению к дефолтным долям, а автоопределение применяется
  только при её отсутствии.
- При малом `<CTX>` верхние ступени могут упираться в предел слота: измените
  сетку (например, добавьте ступень) или задайте ступени в токенах.
- В отчёте указывайте и долю, и фактическое число токенов (`prompt_tokens`).

### 4.6. A/B-режим

- Две сессии (A и B) чередуются **в одном слоте** по заданному порядку; паттерн
  применяется циклически, пока обе сессии не пройдут все ступени лесенки.
- Порядок задаётся вызывающим: раннер принимает `--order` (дефолт `ABAB`).
  Нормативный набор порядков для A/B-серии — `ABAB` и `ABBABAA`; требуется
  запуск **обоих** контрактных порядков.
- Сравнение A/B ведётся **по совпадающим ступеням**.
- A/B-замер cache-hit корректен, только если обе сессии помещаются в host
  prompt-кеш (`--cache-ram`). Если не помещаются — замер идёт с вытеснением, и
  A/B для этой конфигурации не выполняется; снимается только одиночная лесенка.
- **Измерено** (пример): при KV-кванте, где две сессии суммарно меньше
  `--cache-ram`, значения cache-hit идентичны для A и B и для обоих порядков.
- **Counterbalance для сравнения конфигураций.** Для A/B **разных
  конфигураций** (со сменой флага и перезапуском сервера) применять чередование
  `A,B,A,B`, а не «все A, потом все B»: последовательные блоки накапливают дрейф
  частот/температур. Для сессионного A/B (ось — порядок обращений внутри одной
  сессии) порядки `ABAB`/`ABBABAA` остаются как выше.

## 5. Полное помещение модели и KV в VRAM

### 5.1. Как проверить

- Флаг полного offload (пример: `-ngl all`); все слои на `<GPU>`.
- `/props` → `n_ctx` совпадает с `<CTX>`.
- Строки `server.log`: `model buffer size`, `KV self size` / `KV buffer size`,
  `compute buffer size`, `RS buffer size`, а также per-device размеры
  (`CUDA0 model buffer size`, …).
- **По каждому устройству** сверить выделение VRAM (model + KV + compute/RS) с
  логом и телеметрией: сумма буферов из лога должна согласовываться со
  спецификацией карты и наблюдаемой VRAM; расхождение фиксируется.
- **Признаком partial offload служит число слоёв:** строка
  `offloaded X/Y layers to GPU`; при X < Y конфигурация помечается как
  **partial offload**, а не «full VRAM», и её скорости не сравниваются с полным
  offload.
- **Информационные поля (НЕ признак partial offload):** непустой
  `CPU_Mapped model buffer size` — это memory-mapped (mmap) веса, а не
  CPU-инференс; `CUDA_Host output/compute buffer size` — тоже не признак.
  Записывать их как информационные поля.
- **Признаки размещения model/KV именно на CPU:** model- или KV-буфер на CPU
  (не `CPU_Mapped`, не `CUDA_Host`) с ненулевым значением (порог > 0.01 MiB).
  При любом таком признаке конфигурация помечается как **partial offload**, а
  не «full VRAM», и её скорости не сравниваются с полным offload.
- Пик VRAM и запас — из телеметрии: пик = максимум `memory.used` по карте за
  прогон; **вычислено:** запас = VRAM карты − пик VRAM. **Запас VRAM ≥ 0 на
  всех ступенях лесенки**, а не только на максимуме; при вытеснении или
  частичном offload прогон помечается статусом `non_comparable` (раздел 7).

### 5.2. Порядок действий, если не влезает

1. Понизить KV-квант (например, `f16` → `q8_0` → `q4_0`).
2. Уменьшить `<CTX>`.
3. Перераспределить слои (`--tensor-split`, `--split-mode layer`) или добавить
   карту.
4. В крайнем случае — отдельная карта под модель.

После каждого шага — снова smoke-проба и проверка запаса. Узкая карта — та, что
упадёт по OOM на более длинном промпте; ориентируйтесь на неё.

### 5.3. Честная маркировка

- **Частичный offload** (`offloaded X/Y` при X < Y; либо model/KV буфер на
  CPU, кроме `CPU_Mapped`/`CUDA_Host`) — явно указывать в отчёте; такие
  числа не сравнивать с полным offload. `CPU_Mapped` — mmap весов, не признак.
- **Вытеснение host prompt-кеша** (строки вида
  `making room for prompt cache entry, removing oldest entry`) — ожидаемо при
  больших KV; помечать, что cache-hit в этом режиме искажён.
- **OOM** — прогон сохраняется как `failed`, причина фиксируется.

## 6. Параллельность 1

- `--parallel 1` — один слот. **Интерпретация:** при одном слоте нет
  конкуренции запросов за слот/батч, тайминги стабильны, а prompt-кеш и A/B
  ведут себя предсказуемо.
- Слоты и prompt-кеш: A/B-сессии делят один слот; `--cache-prompt`,
  `--cache-ram`, `--cache-idle-slots` управляют вытеснением KV в ОЗУ.
- **Concurrency — отдельная ось.** Замеры при `--parallel 1` и `concurrency 1`
  не смешивать с многопоточными/параллельными запросами (`--parallel 2..N`):
  это другой эксперимент с другим ответом (раздел 3).

## 7. Протокол замеров

**Последовательность:** `smoke` → `ladder` → `A/B`.

1. **Smoke** перед каждой волной/серией: загрузка, `/props`, пик VRAM.
2. **Ladder** — основная кривая «скорость против заполнения».
3. **A/B** — контроль переиспользования prompt-кеша и порядка (там, где обе
   сессии помещаются в host-кеш).

### 7.1. Статусы прогонов

Каждый прогон имеет ровно один статус:

| Статус | Условие | В основные таблицы/графики |
| --- | --- | --- |
| `ok` | прогон завершён, инварианты раздела 1 соблюдены | да (по comparable-ступеням) |
| `failed` | ошибка, OOM, падение сервера, отсутствие ожидаемых таймингов | нет (сохраняется как есть) |
| `timeout` | клиентский/серверный таймаут, обрыв до завершения | нет (сохраняется как есть) |
| `non_comparable` | прогон завершён, но нарушен инвариант раздела 1; статус выставляется раннером | нет (сохраняется как есть) |

- **Разделение ответственности.** Раннер выставляет `timeout`/`failed` по типу
  исключения (таймаут — `timeout`, прочее — `failed`) и **помечает** нарушения
  инвариантов (статус `non_comparable` + структурированные причины в
  `status_reasons`, вид `kind=invariant|exception`). Сопоставимость **ступени**
  раннер отражает флагом `step_comparable` (= `completion_is_fixed` AND
  `finish_reason = length` AND `prompt_prefix_ok`), а не статусом прогона.
  Каноничность строится агрегатором **per-ступень** по `step_comparable`.
- **Ступень, а не прогон.** Один прогон ladder может содержать и comparable-, и
  non-comparable-ступени. Поэтому статус прогона по генерации делится на
  `fixed` (все ступени comparable), `mixed` (часть) и `variable` (ни одной);
  агрегатор строит канон по comparable-ступеням, а `mixed`/`variable`-прогоны
  перечисляются отдельным разделом.
- **TIMEOUT отделён от FAILED.** Таймаут — не падение, а обрыв по времени; это
  отдельный статус `timeout`, а не `failed`.
- Прогоны `non_comparable` не «плохие»: они сохраняются, но не попадают в
  основные таблицы и графики.
- **Недоступные обязательные поля телеметрии.** Если обязательное поле
  телеметрии (раздел 10) не собрано — прибор/интерфейс недоступен — прогон
  помечается `non_comparable`, когда это влияет на сопоставимость (например,
  нельзя проверить пик/запас VRAM или температуры). Молчаливый пропуск
  обязательных полей **не допускается**: факт и причина фиксируются в
  `result.json` и отчёте. Пустые значения опциональных полей допустимы и статус
  не меняют.

**Фиксированная генерация.** `temperature 0`, фиксированный `seed`,
`ignore_eos = true` и фиксированный `n_predict` (пример: `<N_PREDICT>`, например
128 токенов). Признак корректности — `finish_reason = length` и
`completion_is_fixed = true`. Ступень с `finish_reason != length` или
`completion_is_fixed != true` получает `step_comparable = false` и в агрегат не
входит (разделы 7.1, 11.1).
**Интерпретация:** без фиксации длины decode несопоставим между прогонами.

**Повторы и прогрев.** Канонический результат ступени требует **n ≥ 3** успешных
(`ok`) прогонов на эту ступень (каноничность per-ступень, раздел 11.1). Для
каждой серии указывать `n` и идентификаторы (`run_id`) всех вошедших прогонов;
агрегация — **медиана + min/max** (раздел 11). При **n < 3** ступень помечается
ограниченной/неканонической: она сохраняется, но не используется для основных
выводов и не подаётся как каноническая. Прогревочный запрос (ступень 0 %) в
анализ не входит.

**Изоляция длинных кейсов.** Длинные промпты в одном серверном процессе делят
префикс, и prefill занижается (**prompt-cache контаминация**). Длинные кейсы
измерять отдельными прогонами при `--repetitions 1`.

**Клиентские таймауты.** Таймаут запроса должен превышать ожидаемый prefill.
Пример (не обязателен): prefill ~250k занимает ~950–1000 с, поэтому жёсткий
таймаут 900 с обрывает прогон. Настраивайте клиентский таймаут и серверный
`--timeout` под свой `<CTX>`; TIMEOUT ≠ падение — это отдельный статус.

## 8. Метрики и их определения

| Метрика | Определение | Источник | Тип |
| --- | --- | --- | --- |
| prefill tok/s | prompt eval tokens / prompt eval time | `prompt eval time = … (… tokens per second)` в `server.log`; `timings.prompt_per_second` | измерено |
| decode tok/s | eval tokens / eval time | `eval time = … (… tokens per second)`; `timings.predicted_per_second` | измерено |
| TTFT | время до первого токена | стриминговый клиент | измерено |
| elapsed | полное время запроса | клиент, end-to-end | измерено |
| `cache_hit_fraction` | доля промпта из кеша | `1 − evaluated/prompt`; `cache_n/(cache_n+prompt_n)` | вычислено |
| пик VRAM | максимум `memory.used` по карте | `telemetry.csv` | измерено |
| запас | VRAM карты − пик VRAM | телеметрия + спецификация | вычислено |
| acceptance | `draft_n_accepted / draft_n`; средняя длина драфта | `timings` / `draft acceptance` в логе | измерено |
| средняя мощность (`power_avg_w`) | суммарная по `<GPU>` мощность, проинтегрированная по окну запроса, / длительность окна | `telemetry.csv` (`gpuN_power_w`); агрегатор | вычислено (оценка) |
| энергия запроса (`energy_j`) | интеграл суммарной мощности по окну запроса (трапеции) | `telemetry.csv`; агрегатор | вычислено (оценка) |
| динамическая энергия (`energy_dynamic_j`) | интеграл `max(0, P − base)`; `base` — минимум суммарной мощности за прогон | `telemetry.csv`; агрегатор | вычислено (оценка) |
| J/output-token (`energy_per_output_token_j`) | `energy_j / completion_tokens` | агрегатор | вычислено (оценка) |
| J/input-token (`energy_per_input_token_j`) | `energy_j / evaluated_tokens` | агрегатор | вычислено (оценка) |

- **Энергия/мощность — оценка.** Телеметрия мощности `gpuN_power_w` у
  потребительских и майнинговых карт грубая, а окно запроса задаётся парой
  `started_at_utc`/`finished_at_utc` и аппроксимируется краевой интерполяцией
  мощности. Энергетические метрики вычисляет агрегатор при наличии
  `telemetry.csv` и меток времени (разделы 10, 11.1); иначе поля пусты.
- **Канонический источник каждой метрики** задан в столбце «Источник». При
  наличии и API-полей `timings.*`, и строк лога сохранять **оба** значения и
  проверять расхождение между ними.
- **Первичность raw server timings задана явно.** Каноническим считается сырой
  серверный тайминг (строка лога); структурированные API-поля `timings.*`
  сохраняются как вторичное подтверждение, а их расхождение с логом фиксируется
  в отчёте. HTTP end-to-end (`elapsed`) — подтверждающая метрика.
- **Результат аудита источников (`docs/timing-source-audit.md`).** API
  `timings.*` и сырой `log_timings` численно **тождественны**: max |delta| =
  0.025%, ни одной пары с |delta| ≥ 0.1% (0/220); расхождение — только потеря
  точности при печати лог-строки до 2 знаков. Поэтому канон не меняется: сырой
  лог первичен, API — вторичное подтверждение. Расхождение фиксируется полем
  `timing_delta_pct`; пороги значимости: |delta| ≥ 0.1% — значимо; 0.05–0.1% —
  серая зона (перепроверить); < 0.05% — норма (округление печати).
- Если поле тайминга отсутствует в этой сборке, брать эквивалент (пример:
  `raw_server_timing.tg` может отсутствовать — decode брать из
  `eval.tokens_per_second`).
- `started_at` в отчёте может означать время сборки отчёта, а не старта прогона:
  не использовать его как метку старта.

## 9. Логирование сервера

- `server.log` сохраняется **без фильтрации** (stdout+stderr сервера) — это
  первоисточник таймингов и предупреждений.
- Парсить: `prompt eval time`, `eval time`, `n_decoded`/`tg`, `draft acceptance`,
  размеры буферов (model/KV/compute/RS), `n_ctx`, `flash_attn`, строки вытеснения
  prompt-кеша.
- **Ожидаемые предупреждения** (не считать ошибкой):

| Предупреждение | Значение |
| --- | --- |
| нет прав на смену частот (`clocks_reset.returncode: 4`, «does not have permission to change clocks») | GPU-частоты не меняются процессом — ожидаемо |
| CORS / отсутствие API-key | сервер слушает локально; ключ не нужен |
| reasoning preserve «enabled by default» | профиль задаёт `--reasoning off`; на замеры не влияет |
| `making room for prompt cache entry, removing oldest entry` | вытеснение host prompt-кеша при больших KV — ожидаемо |
| `rope_finetuned = unknown` | поле метаданных GGUF; не ошибка и не предупреждение об архитектуре |
| `srv stop: cancel task, id_task = …` | штатная остановка сервера по завершении прогона |

- **Что НЕ считать ошибкой:** ожидаемые предупреждения из таблицы выше.
- **Что считать ошибкой:** OOM, падение сервера, отсутствие ожидаемых
  таймингов, `Xid`/`AER` в журнале ядра.

## 10. Телеметрия

- **Нормативный формат (версия схемы 1).** Один формат `telemetry.csv` с
  заголовком; каденс 0.5 с; сэмплы пишутся в течение всего прогона.
- **Машиночитаемая версия схемы.** Первая колонка/поле CSV — `schema_version`
  со значением `1`. Потребитель **обязан** проверять `schema_version` перед
  интерпретацией; при несовпадении файл **не интерпретируется** как схема 1.
- **Число `<GPU>` — динамическое:** колонки `gpuN_*` повторяются для каждого
  устройства `N` из `<GPU_LIST>`, а не жёстко `gpu0`–`gpu2`.
- **Колонки** (О — обязательные, о — опциональные); точный нормативный список:

| Группа | Колонки |
| --- | --- |
| Схема | `schema_version` (О; всегда `1`, первая колонка) |
| Время | `timestamp_utc` (О, ISO-8601 UTC) |
| Хост | `cpu_pct` (О); `cpu_temp_c` (О) + `cpu_temp_source` (О); `ram_used_gib` (О), `ram_total_gib` (О), `swap_used_gib` (О) |
| Per-core | `cpuN_pct` (О; динамически по числу логических ядер: `cpu0_pct`, `cpu1_pct`, …) |
| Per-`<GPU>` | `gpuN_temp_c`, `gpuN_util_pct`, `gpuN_mem_used_mib`, `gpuN_power_w`, `gpuN_sm_clock_mhz` (О); `gpuN_pstate` (о) |
| Процесс сервера | `server_rss_kib`, `server_pss_kib`, `server_swap_kib` (О; сумма по процессам сервера); `llama_pids` (о) |

- **Снимки частот — метаданные, а не телеметрия.** `clocks_sm_before` /
  `clocks_sm_after` записываются **один раз за прогон** в `result.json`
  (метаданные), а **не** в `telemetry.csv`.
- **Формат значений:** CSV с заголовком; числовые значения — с фиксированной
  точностью. Пустые значения допустимы **только для опциональных** полей;
  обязательное поле при недоступном приборе/интерфейсе не пропускается молча —
  см. правило статуса в разделе 7.1.
- **Синхронизация временем:** метки времени — в UTC, чтобы сопоставлять
  телеметрию с `server.log`.
- **`gpuN_power_w` — источник энергии.** Интеграл суммарной мощности по
  ступени (раздел 8) считается агрегатором из этих колонок; окно запроса
  задаётся парой `started_at_utc`/`finished_at_utc` ступени (UTC, синхронно с
  `timestamp_utc`), а сама энергия вычисляется агрегатором
  (`scripts/report/generate_report.py`), **а не** сборщиком телеметрии. Схема
  колонок при этом не меняется.
- **Частоты:** снимать `clocks.sm` (и P-state) до и после прогона; парковка
  `<GPU>` в простое делает замеры недействительными.
- **Канонический сборщик.** `scripts/telemetry/host_telemetry.py` — переносимый
  сборщик методологии (копируется в `<кейс>/scripts/`); он реализует схему 1 и
  вызывается раннером/автономно. Любой другой сборщик, не собирающий per-core и
  SM clock и не пишущий UTC-метку, схеме **не соответствует** и как источник
  телеметрии не используется.

## 11. Агрегация и графики

### 11.1. Выбор канонического прогона и агрегация

Каноническим для конфигурации/ступени считается **агрегат по повторам**, а не
отдельный прогон. При этом каноничность определяется **per-ступень** (не
per-прогон): ступень входит в агрегат только если она comparable по
`step_comparable` (`completion_is_fixed == true` AND `finish_reason = "length"`
AND `step_comparable != false`). Поле `step_comparable` опционально: раннер
формирует его как (`completion_is_fixed` AND `finish_reason = length` AND
`prompt_prefix_ok`), поэтому для **новых** прогонов действуют все три условия.
Агрегатор (`scripts/report/generate_report.py`, `step_is_comparable`)
`prompt_prefix_ok` напрямую **не проверяет** и для **legacy**-прогонов без поля
`step_comparable` опирается на первые два условия.

1. Исключить прогоны со статусами `failed`, `timeout`, `non_comparable`, а
   внутри `ok`-прогонов — ступени, не прошедшие `step_comparable`.
2. Медиана/min/max считаются **только по comparable-ступеням**; канонический
   результат ступени требует **n ≥ 3** уникальных прогонов на эту ступень.
   Исключённые ступени **не отбрасываются молча**, а перечисляются с причиной
   (статус/`finish_reason`/`completion_is_fixed`).
3. Ступени с **n < 3** помечаются `limited` и **не входят в основные таблицы и
   графики** — выводятся отдельным разделом.
4. `n` ступени = число **уникальных** прогонов на эту ступень; вклад одного
   прогона в одну `target_pct` не дублируется. Профильный `n` = число прогонов,
   у которых есть **≥ 1** comparable-ступень.
5. Документировать `n` и список `run_id` всех вошедших прогонов.

Статус прогона по генерации делится на `fixed`/`mixed`/`variable` (раздел 7.1):
у `mixed`-прогонов comparable-ступени входят в агрегат, а исключённые
перечисляются отдельно.

Агрегацию выполняет переносимый `scripts/report/generate_report.py` (копируется в
`<кейс>/scripts/`): он читает сырые прогоны, исключает `failed`/`timeout`/
`non_comparable`, per-ступень применяет `step_comparable` и считает медиану и
min/max по повторам, документируя `n` и `run_id`; limited-ступени выводятся
отдельно. Нормативный минимум — агрегация по повторам, как описано выше.

Энергетические метрики (`energy_j`, `energy_dynamic_j`, `power_avg_w`,
`energy_per_output_token_j`, `energy_per_input_token_j`,
`energy_per_output_token_j_dynamic`) агрегируются наравне с базовыми: медиана
+ min/max по comparable-ступеням, с `n` и `run_id`; они входят в
машинно-читаемую сводку `results.json` (per-step `metrics`) и в отдельную
таблицу отчёта. Пустые значения (нет `telemetry.csv` или меток времени)
игнорируются, а не считаются нулём.

**Парный A/B-Δ.** Сравнение A/B считается не по отдельным медианам A и B, а по
парам совпадающих ступеней внутри одного `ab-sequence`-прогона: для одного
`target_pct` и порядка (`order`) сопоставляются comparable-ступени сессий A и
B, `delta_pct = 100·(B−A)/A`; агрегат пары — медиана Δ, число пар `n_pairs` и
`sign_consistency` (доля пар, знак Δ которых совпадает со знаком медианы).
Ступень прогрева `0 %` исключена; разные порядки и ступени не смешиваются.
Результат сохраняется в `results.json` под ключом `"profile|order"`.

### 11.2. Графики

Правило обязательности: график обязателен **при наличии соответствующей
измеренной серии**; если серия не измерялась, график не строится, а причина
фиксируется в отчёте. Отсутствие обязательного графика при наличии серии
требует объяснения. Каждый график — RU и EN.

Графики делятся на две группы.

**(а) Автоматически генерируемые фигуры.** Плоттер
`scripts/report/plot_context_curves.py` строит пять фигур (файлы
`<имя>.<lang>.svg`): базовые три — при условиях «как есть», две
потребления (`power-vs-load`, `energy-per-token`) — при наличии
энергетической серии; иначе выводится предупреждение, и фигура не строится.

| Фигура (имя файла) | Условие обязательности |
| --- | --- |
| `prefill-vs-context` | если измерялась лесенка (ядро методики) |
| `decode-vs-context` | если измерялась лесенка (ядро методики) |
| `ab-cache-hit` | при наличии A/B-серии |
| `power-vs-load` (средняя мощность против заполнения) | при наличии энергетической серии |
| `energy-per-token` (J/output-token против заполнения) | при наличии энергетической серии |

**(б) Дополнительные графики по осям.** Автор строит их **отдельно** (вне
`plot_context_curves.py`) при наличии соответствующей серии:

| График | Условие обязательности |
| --- | --- |
| раскладка vs prefill | при наличии серии по раскладке |
| ubatch (prefill/decode против `--ubatch-size`) | при наличии серии по ubatch |
| глубина спекуляции (decode/acceptance против глубины) | при наличии серии по спекуляции |

- Если серия не измерялась, соответствующий график не строится, и причина
  фиксируется в отчёте.
- Формат — **SVG** (без внешних зависимостей), отдельные файлы для RU и EN.
- **Машинно-читаемая сводка** `results.json` и таблицы `results-tables.md` —
  генерируются из сырых прогонов; агрегаторы read-only по отношению к прогонам.
- **Правила подписей:** отделять измеренное от вычисленного (проценты, Δ,
  запас — «вычислено»); указывать конфигурацию, `<CTX>`, KV-квант и рантайм;
  не сглаживать кривые без пометки.
- **Переносимые агрегаторы.** `scripts/report/generate_report.py` (сводка
  `results.json` + таблицы `results-tables.md`) и
  `scripts/report/plot_context_curves.py` (графики) копируются в
  `<кейс>/scripts/`. Серии, подписи и роли (`main`/`control`) берутся из
  конфига `study.json` (или автоопределяются из сырых прогонов, если конфига
  нет); зашитых профилей и labels нет.
- **Конфиг `study.json`.** Задаёт название исследования, список профилей
  (`name`/`label`/`role`), `ab_planned` (профили с обязательной A/B-серией),
  `ab_orders` (ожидаемые порядки) и `ladder_pcts` (ступени лесенки в % от
  `<CTX>`). Любой из списков необязателен: при отсутствии конфига агрегаторы
  автоопределяют профили, порядки и ступени, все профили становятся `main`.

## 12. Артефакты прогона и исследования

**Каждый прогон** пишет каталог `results/<run_id>/`:

| Файл | Содержимое |
| --- | --- |
| `result.json` | `run_id`, статус (`ok`/`failed`/`timeout`/`non_comparable`), ошибка, ступени (prefill/decode, cache-hit, `completion_is_fixed`, `finish_reason`), максимумы телеметрии, `clocks_*` |
| `profile.json` | копия использованного профиля |
| `command.json` | фактическая команда, окружение, порт, seed, режим/порядок |
| `server.log` | stdout+stderr сервера (буферы, предупреждения, вытеснение) |
| `telemetry.csv` | сэмплы каждые 0.5 с (раздел 10) |

**Исследование** дополнительно содержит:

- агрегированные сводки (`results.json`, `results-tables.md`) и графики;
- хронологию фаз (что и когда измерено, включая негативные результаты);
- провенанс модели и рантаймов (sha256, commit, флаги сборки);
- прогоны со статусами `failed`/`timeout`/`non_comparable` и текстом причины.

## 13. Портируемость

| Категория | Что относится | Сопоставимость |
| --- | --- | --- |
| Обязательно фиксировать | модель/`<GPU>` (модель, VRAM, число, топология, линки), CPU/RAM, драйвер, CUDA, commit `<RUNTIME>`, sha256 `<MODEL>` | без этого сравнение невозможно |
| Железозависимо (локальный свип) | `--ubatch-size`, `--tensor-split`, глубина спекуляции, порядок устройств | оптимум переносить нельзя, только пересвипывать |
| Сравнимо между стендами | только одинаково определённые нормированные показатели при совпадающей семантике (например, относительные Δ между конфигурациями внутри одного стенда, одинаково определённый `cache_hit_fraction`) | относительно |
| Не сравнимо между стендами | абсолютные tok/s, форма performance-кривой (зависит от рантайма/драйвера/частот/токенизатора), оптимальная раскладка, пороги OOM | только локально |

**Вывод.** Сравнивать преимущественно **внутри стенда**; межстендово сопоставимы
только одинаково определённые нормированные показатели при совпадающей
семантике. Абсолютные числа и форма кривой — только внутри одного стенда,
одного рантайма и одной конфигурации частот.

## 14. Агентный workflow

- **Роли:** оркестратор (`keeper`) — планирует и принимает; `sys-probe` —
  железо/окружение; `bench-rig` — прогоны; `runtime-build` — сборка движка;
  `model-fetch` — загрузка/проверка весов; `code-smith` — код; `net-researcher`
  — внешние источники; `reviewer` — проверка.
- **Разделение:** исполнение, проверка и интерпретация — разные роли. Исполнитель
  не проверяет себя; ревьюер не правит код.
- **Контракт поручения:** цель → подтверждённый контекст → абсолютный путь →
  scope и запрет выходить за него → задача и ограничения → критерии приёмки →
  формат ответа.
- **Параллелизм ≤3**, только без пересечения файлов/контрактов; фон — с
  реестром задач и дедлайном.
- **Неудачные прогоны сохраняются.** Факт vs интерпретация: раннер возвращает
  дословно (PASS/FAIL/TIMEOUT, exit code, stdout), интерпретирует вызывающий.
- **Git-мутации** (commit/push/checkout/clean) — только по явному запросу
  пользователя.

## 16. Типичные ошибки

Собраны из завершённых кейсов; каждая — с признаком и лечением. Числа ниже —
**case-specific примеры** из конкретных артефактов (см. `inference_cases/`), а не
переносимые факты.

1. **Decode на короткой генерации.** Метрика негодна (мало токенов). Лечение:
   длинная генерация и `ignore_eos` + `n_predict`.
2. **Prompt-cache контаминация.** Длинные кейсы в одном процессе делят префикс,
   prefill занижается. Лечение: отдельные прогоны, `--repetitions 1`.
3. **Idle-парковка частот.** Все замеры недействительны. Case-specific пример:
   300 МГц (см. артефакт). Лечение: снять парковку, снимать `clocks.sm`
   до/после.
4. **Клиентский таймаут.** Меньше времени prefill — обрыв до завершения.
   Лечение: таймаут по кейсу, а не жёсткое значение.
5. **Фиксированные накладные спекуляции/MTP.** Case-specific пример: ~2.8 с на
   запрос (см. артефакт), что вредит коротким прибавкам к длинному контексту.
   Лечение: отделять фиксированные накладные от маргинальной стоимости.
6. **Вытеснение host prompt-кеша.** KV больше `--cache-ram` — A/B cache-hit
   искажён. Лечение: A/B только когда обе сессии помещаются.
7. **OOM при большом µbatch.** Case-specific пример: `--ubatch-size 1024` при
   большом `<CTX>` даёт OOM на узкой карте (см. артефакт). Лечение: локальный
   свип µbatch и контроль запаса VRAM.
8. **Неполный offload.** Часть слоёв на CPU (`offloaded X/Y` при X < Y; либо
   model/KV буфер на CPU, кроме `CPU_Mapped`/`CUDA_Host`) — скорости не
   сопоставимы. `CPU_Mapped` — mmap весов, не признак CPU-инференса.
   Лечение: проверить буферы и запас до замеров.
9. **Confounded-свипы.** Несколько параметров меняются одновременно (пример:
   µbatch вместе с KV-квантом и переменными окружения). Лечение: одна ось за
   раз; иначе вывод помечать как несопоставимый.
